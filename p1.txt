## 7. Design the Database Schema

Create the following PostgreSQL tables using Drizzle ORM.

### A. users

Fields:

* id: UUID primary key
* name: required string
* email: required and unique
* password_hash: required string
* created_at: timestamp
* updated_at: timestamp

Requirements:

* Store only hashed passwords.
* Email must be unique.
* Normalize email before storing it.
* Never return password_hash in API responses.

### B. centres

Fields:

* id: UUID primary key
* name: required string
* location: required string
* created_at: timestamp
* updated_at: timestamp

### C. tests

Fields:

* id: UUID primary key
* centre_id: foreign key referencing centres
* name: required string
* description: optional string
* price: numeric/decimal
* created_at: timestamp
* updated_at: timestamp

Requirements:

* A centre can offer multiple tests.
* Each test belongs to one centre in this initial design.
* Price must be positive.
* Use appropriate foreign-key constraints.
* Avoid floating-point types for money.

### D. bookings

Fields:

* id: UUID primary key
* user_id: foreign key referencing users
* test_id: foreign key referencing tests
* centre_id: foreign key referencing centres
* appointment_at: timestamp with timezone
* amount: numeric/decimal
* status: booking status
* created_at: timestamp
* updated_at: timestamp

Booking statuses:

* PENDING
* CONFIRMED
* FAILED
* CANCELLED

Requirements:

* Booking must reference an existing user.
* Booking must reference a valid test and centre.
* Amount must be positive.
* Save the booking amount at booking creation time.
* Do not allow arbitrary client-provided amounts.
* Use appropriate database indexes.

### E. payments

Fields:

* id: UUID primary key
* booking_id: foreign key referencing bookings
* amount: numeric/decimal
* status: payment status
* provider_event_id: nullable initially, unique when present
* created_at: timestamp
* updated_at: timestamp

Payment statuses:

* PENDING
* SUCCESS
* FAILED

Requirements:

* A booking may have multiple payment attempts.
* A booking must not have multiple successful payments.
* Prevent duplicate webhook event IDs.
* Add appropriate indexes and constraints.
* Explain how the schema supports payment retries.

For database enums or check constraints, choose an approach compatible with PostgreSQL and Drizzle migrations.
